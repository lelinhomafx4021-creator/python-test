# 44_上下文工程：Prompt Engineering 的下一代

> **核心目标**: 理解 Context Engineering 是什么、和 Prompt Engineering 的区别、四种核心策略
> **为什么重要**: LangChain 官方 2026 年重点推的概念。面试加分利器——大多数候选人只会说 Prompt Engineering。

---

## 一、Context Engineering vs Prompt Engineering

```
Prompt Engineering（2023-2025）:
  关注 "怎么把指令写好"
  → system prompt 怎么措辞
  → few-shot 例子怎么选
  → 输出格式怎么约束

Context Engineering（2026+）:
  关注 "怎么管理 LLM 看到的所有信息"
  → 不只是 system prompt，还包括历史消息、检索结果、工具输出
  → 有限上下文窗口（128K token）里的信息优先级
  → 上下文太长时怎么压缩、太乱时怎么组织
```

**一句话**：Prompt Engineering 关心"说什么"。Context Engineering 关心"给多少、怎么给、什么时候给"。

---

## 二、为什么需要 Context Engineering

### 2.1 上下文窗口不是无底洞

```
DeepSeek-v4: 128K token 上下文窗口

看起来很大，但实际上：
  system prompt:         ~500 tokens
  历史消息 10 轮:       ~3000 tokens
  检索到的文档块 × 5:   ~2500 tokens
  行情数据 + 财务数据:    ~800 tokens
  工具调用的返回值:       ~2000 tokens
  LLM 的输出累积:        ~4000 tokens
  ─────────────────────────────
  合计:                 ~12800 tokens  ← 看起来还很远

但多轮对话后:
  历史消息 30 轮:       ~15000 tokens
  每次检索 × 多轮累积:   ~10000 tokens
  ─────────────────────────────
  合计:                 ~30000+ tokens

问题不只是"装不下"，更是 "装得下但 LLM 注意力分散"。
上下文越长，LLM 越容易忽略关键信息。
```

### 2.2 各种信息的优先级不同

```
LLM 看到的信息:
  [System Prompt]        ← 最重要，行为约束
  [历史消息 × N 轮]       ← 提供上下文，但越旧越不重要
  [本轮检索结果 × 5 条]   ← 关键，答案的依据
  [行情数据]              ← 辅助
  [工具调用的中间结果]     ← 对当前这步有价值，对后面的步没有
```

**Context Engineering 做的事**：不是把所有信息一股脑扔给 LLM，而是按优先级组织、压缩不重要的、隔离不该看的。

## 三、四大策略（The 4 Acts）

LangChain 官方提出的 Context Engineering 四大策略：

### Act 1: Write Context（写入上下文）

**做什么**：决定**什么信息**应该放进上下文。

```
反例（不做 Write Context）:
  把整个搜索结果页（含广告、导航栏）全部塞给 LLM
  → LLM 看到一堆无关内容，答案被稀释

正例（做 Write Context）:
  搜索结果 → 只提取标题+正文+来源 → 统一格式 → 喂给 LLM
  → LLM 看到干净、结构化的信息
```

**项目里已经在做的**：`to_prompt_context()` 方法——把 Skill 输出的 dict/list 格式化成 LLM 能读的文本。这就是 Write Context。

```python
# app/skills/stock_analysis_skill.py
def to_prompt_context(self) -> str:
    """把结构化数据变成 LLM 可读的上下文"""
    return (
        f"【检索知识】\n{self.knowledge}\n\n"     # 只取相关的
        f"【实时行情】\n{quote_text}\n\n"          # 结构化后注入
        f"【证据清单】\n{evidence_text}"           # 审计追踪
    )
```

### Act 2: Isolate Context（隔离上下文）

**做什么**：把不该让 LLM 看到的信息**隔离开**。

```
场景 1: 工具调用的中间结果
  调了 get_quote → 拿到 {"price": 1856, "volume": ...}
  调了 get_financials → 拿到 {"pe": 35, "revenue": ...}
  调了 get_news → 拿到 [一堆新闻标题]
  
  全部扔给 LLM → 混乱，不知道哪个数据对应哪个来源

  Isolate Context 的做法:
    market_data = state["market_data"]      # 存 state 里，不直接喂给 LLM
    financial_data = state["financial_data"] # 同上
    → answer_node 只通过 skill_context 拿到格式化后的文本

场景 2: 多 Agent 之间的上下文
  Agent A（研究员）查了一堆资料
  Agent B（写手）只需要研究员的结构化摘要
  → 不应该把 Agent A 的全部中间结果传给 Agent B
  → LangGraph 的 state 天然支持隔离：每个子图有自己的 state schema
```

**项目里已经在做的**：`fetch_data_node` 把行情/财务/公告分别存进 state 的不同字段，`answer_node` 只读 `skill_context`（格式化后的文本）。这就是 Isolate Context。

### Act 3: Compress Context（压缩上下文）

**做什么**：当上下文太长时，**压缩不重要的信息**。

#### 方法 1: 截断压缩 — 只保留最近 N 轮

```python
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES

async def compress_by_trim(config, keep_last_n_pairs=5):
    """只保留最近 N 轮对话，其余删除"""
    state = await graph.aget_state(config)
    messages = state.values["messages"]

    if len(messages) <= keep_last_n_pairs * 2:  # 每轮 = 用户消息 + AI 回复
        return  # 不需要压缩

    # 保留: 第一条（可能是 system 或 最初的用户问题）+ 最近 N 轮
    keep_count = keep_last_n_pairs * 2
    old_ids = [m.id for m in messages[:-keep_count]]

    await graph.aupdate_state(
        config,
        {"messages": [RemoveMessage(id=mid) for mid in old_ids]}
    )
    print(f"截断压缩: 删除了 {len(old_ids)} 条旧消息，保留最近 {keep_count} 条")


# 使用示例
config = {"configurable": {"thread_id": "user_1001"}}
# ... 对话进行了 50 轮 ...
await compress_by_trim(config, keep_last_n_pairs=5)
# 继续对话
result = await graph.ainvoke(None, config)
```

#### 方法 2: 摘要压缩 — LLM 总结旧消息

```python
from langchain_core.messages import HumanMessage, AIMessage, SystemMessage

async def compress_by_summary(config, keep_last_n_pairs=5):
    """用 LLM 把旧消息总结成一段摘要，注入 system prompt"""
    state = await graph.aget_state(config)
    messages = state.values["messages"]

    keep_count = keep_last_n_pairs * 2
    old_msgs = messages[:-keep_count]      # 要被压缩的
    recent_msgs = messages[-keep_count:]    # 保留的

    if not old_msgs:
        return  # 消息太少，不需要压缩

    # ⭐ LLM 把旧对话总结成一段摘要
    summary_prompt = (
        "请用 3-5 句话总结以下对话的关键信息，包括：用户问了什么、你回答了什么、用户有什么偏好。\n\n"
    )
    for m in old_msgs:
        role = "用户" if isinstance(m, HumanMessage) else "AI"
        summary_prompt += f"[{role}]: {m.content}\n"

    summary_response = await llm.ainvoke(summary_prompt)
    summary = summary_response.content

    # 删掉旧消息 + 注入摘要
    old_ids = [m.id for m in old_msgs]

    await graph.aupdate_state(config, {
        "messages": [
            RemoveMessage(id=mid) for mid in old_ids
        ] + [
            SystemMessage(content=f"[历史对话摘要] {summary}"),
        ] + recent_msgs,  # 保留最近几轮的完整对话
    })

    print(f"摘要压缩: {len(old_msgs)} 条旧消息 → 1 段摘要")
    print(f"摘要内容: {summary}")


# 使用示例
# ... 对话 50 轮后 ...
await compress_by_summary(config, keep_last_n_pairs=5)
# LLM 看到的:
#   [System] [历史对话摘要] 用户主要关注茅台和五粮液的股价对比...
#   [Human] 最近的问题...
#   [AI] 最近的回答...
```

#### 方法 3: 混合压缩 — 不同消息类型不同策略

```python
from langchain_core.messages import ToolMessage

async def compress_smart(config, max_total_messages=20):
    """查到的数据不压缩，闲聊历史可以压缩"""
    state = await graph.aget_state(config)
    messages = state.values["messages"]

    if len(messages) <= max_total_messages:
        return

    to_remove = []

    for m in messages[:-max_total_messages]:
        if isinstance(m, ToolMessage):
            # ⭐ 工具返回的数据不压缩（事实性数据，丢了就丢了准确性）
            continue
        to_remove.append(m.id)

    if to_remove:
        await graph.aupdate_state(
            config,
            {"messages": [RemoveMessage(id=mid) for mid in to_remove]}
        )
        print(f"智能压缩: 删除了 {len(to_remove)} 条旧对话，保留了工具返回的数据")
```

#### 方法 4: LangChain 内置 `SummarizationMiddleware`（最省事）

```python
from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware, ContextTokens

agent = create_agent(
    model=llm,
    tools=[...],
    middleware=[
        SummarizationMiddleware(
            context_size=ContextTokens(100000),  # 100K token 时触发压缩
            # LLM 自动总结旧消息 → 注入摘要 → 继续
        ),
    ],
)

# 什么都不用管，Agent 自动在上下文快满时压缩历史。
# 内部做的事就是"方法 2"——LLM 总结旧消息。
```

**三种策略的取舍**：

| 方法 | 代码量 | Token 消耗 | 信息损失 | 适用 |
|------|------|------|------|------|
| 截断 | 10 行 | 零 | 旧消息全部丢失 | 简单场景 |
| 摘要 | 30 行 | 一次 LLM 调用 | 旧消息细节丢失，保留要点 | 通用推荐 |
| 混合 | 25 行 | 零 | 闲聊丢失，数据保留 | 投研/数据密集场景 |
| 内置中间件 | 3 行 | 同摘要 | 同摘要 | 用 create_agent 的项目 |

### Act 4: Route Context（路由上下文）

**做什么**：根据任务类型，**给不同的 LLM 不同的上下文**。

```
场景: 同一个 Agent，不同任务需要不同的上下文

用户问 "你好"（寒暄）:
  → 不需要知识库检索结果
  → 不需要行情数据
  → 只需要 system prompt + 历史消息

用户问 "茅台股价"（投研查询）:
  → 需要知识库检索结果
  → 需要实时行情数据
  → 需要 system prompt + 历史消息 + 检索 + 行情

Route Context:
  不是把所有信息全部发——而是根据意图只发需要的。
```

**项目里已经在做的**：`route_intent` 决定走 `use_kb` 还是 `no_kb` 路线。VIP 用户比普通用户多拿到更深的检索结果和行情数据。这就是 Route Context。

## 五、缓存策略：省 Token 的四种缓存

Context Engineering 最省钱的策略不是压缩——是**根本不让 LLM 看到重复的东西**。缓存就是这个思路。

### 5.1 为什么缓存是上下文工程的一部分

```
没有缓存:
  用户 A: "茅台 PE 多少" → LLM 调用 → 回答
  用户 B: "茅台 PE 多少" → LLM 调用 → 回答  ← 和 A 的问题完全一样
  用户 A: "茅台 PE 现在呢" → LLM 调用 → 回答  ← 和刚才几乎一样
  
  三次调 LLM，花了 3 次 Token
  上下文窗口被 3 次相同的回答挤占

有缓存:
  第 1 次: 调 LLM → 存缓存
  第 2 次: 命中缓存 → 不调 LLM → 省 Token
  第 3 次: 相似但不完全相同 → 看缓存策略
```

### 5.2 四种缓存级别

```
Level 1: 精确匹配缓存（Exact Match）
Level 2: 语义相似缓存（Semantic Cache）
Level 3: 模板缓存（Template Cache）
Level 4: 部分结果缓存（Partial Result Cache）
```

### Level 1: 精确匹配缓存

```python
import hashlib
cache: dict[str, str] = {}

def get_cached_or_call(query: str, llm_fn) -> str:
    key = hashlib.md5(query.encode()).hexdigest()

    if key in cache:
        return cache[key]  # ← 不调 LLM，零 Token 消耗

    result = llm_fn(query)
    cache[key] = result
    return result
```

**适用**：完全相同的 query 重复出现（如 FAQ 场景、热门股票查询）。**不适用**：表述不同但意思相同（"茅台 PE" vs "茅台估值多少" → 精确匹配 miss）。

### Level 2: 语义相似缓存（Semantic Cache）

不做精确字符串匹配——做 embedding 相似度匹配：

```python
import numpy as np

class SemanticCache:
    def __init__(self, embeddings_fn, threshold=0.95):
        self.embeddings_fn = embeddings_fn
        self.threshold = threshold
        self.store: list[dict] = []  # [{embedding, result}]

    def get(self, query: str) -> str | None:
        query_vec = self.embeddings_fn(query)

        for entry in self.store:
            sim = np.dot(query_vec, entry["embedding"])
            if sim > self.threshold:  # 相似度 > 95%
                return entry["result"]  # ← 语义相同，命中缓存

        return None

    def put(self, query: str, result: str):
        vec = self.embeddings_fn(query)
        self.store.append({"embedding": vec, "result": result})
```

```
"茅台 PE 多少"       → embedding: [0.1, 0.3, ...]
"茅台估值是多少"     → embedding: [0.11, 0.31, ...]  ← 相似度 96% → 命中！
"茅台现在什么价格"   → embedding: [0.5, -0.2, ...]   ← 相似度 40% → 不命中
```

**成本**：精确匹配 0 成本。语义匹配需要一次 embedding 调用（~0.001 元 vs LLM 调用 ~0.01-0.05 元，仍然便宜 10-50 倍）。

**坑**：threshold 设太低（比如 0.8），"茅台 PE" 可能命中 "腾讯 PE" 的缓存。
**建议**：threshold 从 0.95 起步，根据场景下调。

### Level 3: 模板缓存

很多 LLM 调用其实有固定的"骨架"：

```python
# 不缓存整个回答，缓存"回答的骨架"
template_cache = {
    "stock_brief": """
        【基本信息】{stock_name} ({stock_code})，{exchange}
        【当前价格】{current_price} 元
        【涨跌幅】{change_pct}%
        【市盈率】{pe}
        【总市值】{market_cap} 亿
    """,
    "market_overview": """
        今日{market_name}：{index_value}，{change_desc}。
        上涨{up_count}家，下跌{down_count}家。
        {hot_sector}板块领涨，{cold_sector}板块领跌。
    """,
}

# 使用: 数据填充模板 → 直接返回，不调 LLM
def answer_stock_brief(data: dict) -> str:
    return template_cache["stock_brief"].format(**data)
```

**适用**：结构化数据填充场景——行情播报、定时推送、标准化报告。模型只需要总结或分析时才出马。

### Level 4: 部分结果缓存

```python
# RAG 场景: 文档向量不需要每次重建
class RAGCache:
    def __init__(self):
        self.embedding_cache: dict[str, list[float]] = {}  # 文本 → 向量

    def get_embedding(self, text: str) -> list[float]:
        key = hashlib.md5(text.encode()).hexdigest()
        if key not in self.embedding_cache:
            self.embedding_cache[key] = call_embedding_api(text)
        return self.embedding_cache[key]

# 文档不变 → embedding 不变 → 缓存住
# 省的不只是 Token，还有网络延迟（本地查 vs API 调用 ~200ms）
```

### 5.3 缓存策略选型

```
你的场景 → 选哪级缓存？

FAQ 机器人 / 客服:
  → Level 1 (精确匹配) + Level 2 (语义缓存)
  → 热门问题命中率 60-80%

投研 Agent（我们项目）:
  → Level 3 (模板缓存) 行情、财务数据填充用
  → Level 4 (部分结果缓存) embedding 向量缓存
  → 不适合 Level 2 (投研问题太长，语义相似度匹配不准)

代码生成 Agent:
  → Level 4 (部分结果缓存) 工具描述不变 → 不变
  → Level 1 偶尔能用（重复的代码生成请求）

通用场景:
  → 先上 Level 1（零成本），观测命中率
  → 命中率 < 5% → 不加了，不值得
  → 命中率 > 10% → 加 Level 2
```

### 5.4 投产注意事项

```python
# ❌ 千万不要做的事情:
cache = {}  # 全局 dict → 进程重启全丢，内存无限增长

# ✅ 生产环境:
# 方案 A: Redis + TTL
import redis
r = redis.Redis()
r.setex(f"llm_cache:{key}", 3600, result)  # 1 小时后自动过期

# 方案 B: LRU 内存缓存（Python 3.2+）

@lru_cache(maxsize=1000)  # 最多 1000 条，自动淘汰最久未用的
def cached_llm_call(query: str) -> str:
    return expensive_llm_call(query)
```

## 六、面试速记

**Q: Context Engineering 和 Prompt Engineering 有什么区别？**
A: Prompt Engineering 关注"说什么"——system prompt 怎么写、few-shot 怎么选。Context Engineering 关注"给多少、怎么给、什么时候给"——上下文窗口是有限的，要管理好 LLM 看到的所有信息。四个策略：Write（写什么进去）、Isolate（隔离不该看的）、Compress（压缩太长的）、Route（不同任务给不同上下文）。

**Q: 你们的 Agent 长对话怎么处理上下文溢出？**
A: 目前依赖 LangGraph checkpointing——对话历史存在 PostgreSQL 里，同一个 thread_id 自动加载。但超过 30 轮后没有主动压缩，这是已知的技术债。计划用摘要压缩——旧消息用 LLM 总结成几句话，保留最近 10 轮的完整消息。

**Q: Context Engineering 四个策略里，哪个最重要？**
A: 场景不同优先级不同。对话长的系统，Compress 最重要。多数据源的系统，Isolate 最重要。对我们投研系统，Route Context 最重要——闲聊和投研查询需要的上下文完全不同，混在一起 LLM 找不到重点。

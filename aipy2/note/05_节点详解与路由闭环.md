# 05 节点详解与路由闭环

## 1. 当前图里有哪些核心节点

这个项目的主节点大致可以理解为：

1. `route_intent_node`
2. `direct_answer_node`
3. `rewrite_node`
4. `search_node`
5. `answer_node`
6. `critic_node`

它们不是“随便拆的函数”，而是按职责拆开的工作环节。

## 2. `route_intent_node`

职责：判断用户问题要不要走知识库。

它回答的问题不是“用户问了什么全部细节”，而是：

- 这是闲聊吗？
- 这是投研问题吗？
- 需不需要知识检索？

所以它更像一个路由决策器。

## 3. `direct_answer_node`

职责：对于不需要知识库的问题，直接回答。

它适合：

1. 问候
2. 简单说明
3. 无需外部证据的普通问答

但这里也要注意：

- 如果 prompt 把回答限制为 1-3 句
- 那它再聪明也不会给你长文

这就是为什么“路由命中 direct_answer”和“回答长度受 prompt 控制”是两个不同层次的问题。

## 4. `rewrite_node`

职责：把用户问题改写成更适合检索的查询。

为什么不直接拿原问题去查？

因为用户话术可能：

1. 太口语化
2. 太含糊
3. 带很多噪音
4. 不利于向量检索或 web 搜索

所以 rewrite 的核心价值是“把自然问句转成检索语言”。

## 5. `search_node`

职责：调用 RAG / 搜索 / skill，拿到可用知识。

这一步不是让模型幻想，而是先找依据。

它通常会做：

1. 向量检索
2. BM25 检索
3. Web 搜索
4. 行情工具调用
5. 结果融合

## 6. `answer_node`

职责：基于证据生成回答。

这里大模型不再是“自由发挥”，而是要在知识约束下回答。

这也是 RAG 的核心：

- 不让模型只靠参数记忆
- 而是让它引用当前检索到的上下文

## 7. `critic_node`

职责：评审答案质量。

critic 会看：

1. 回答是否贴题
2. 是否使用了检索知识
3. 是否足够可靠
4. 是否需要重试

这一步很像一个审稿人。

## 8. 为什么 critic 很有价值

没有 critic 时，流程一般是：

- 检索一次
- 回答一次
- 直接结束

有 critic 后，系统多了“自我校验”能力：

- 回答不好就打回
- 再改写 / 再检索 / 再回答

这就是 Self-RAG 的闭环味道。

## 9. 条件路由是怎么闭环的

### 第一段

`intent -> use_kb / no_kb`

### 第二段

`critic -> retry / end`

这种设计意味着：

1. 先决定是否检索
2. 再决定是否重试

于是整张图就变成了一个“有入口选择 + 有质量反馈”的工作流，而不是线性流水线。

## 10. 为什么这套节点拆分值得学

因为它体现了 Agent 设计里最关键的一个原则：

> 一个节点只干一种逻辑明确的事。

这样做好处很多：

1. 容易测试
2. 容易观测
3. 容易替换
4. 容易做多智能体演进

## 11. 这一篇你最该记住的结论

1. 节点不是越少越好，而是职责越清晰越好。
2. `intent` 解决路由问题，`critic` 解决质量问题。
3. 当前系统的智能感，很大程度来自“节点分工 + 回退闭环”。

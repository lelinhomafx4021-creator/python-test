# 03a API 与 Service 编排

## 1. 为什么要单独学这一层

很多人看 Agent 项目时，会直接冲进 `graph` 或 `tool`，结果很快迷路。

真正更稳的顺序是：

1. 先看请求怎么进来
2. 再看谁把请求交给 Agent
3. 再看 Graph 内部怎么跑

所以 API 和 Service 层是连接“外部世界”和“Agent 大脑”的桥。

## 2. API 层到底负责什么

`app/api/v1/chat.py` 的职责通常包括：

1. 接收 HTTP 请求
2. 做基础参数校验
3. 把请求转成内部调用
4. 对外返回同步或流式响应

这层不应该承担太多业务判断，更不应该自己写一大堆 RAG 或图逻辑。

## 3. 为什么 `/chat` 和 `/chat/stream` 要分开

因为它们虽然都叫“问答”，但返回方式完全不同。

### `/chat`

- 一次性返回最终结果

### `/chat/stream`

- 持续返回阶段事件和正文增量

这两种模式的体验、实现和异常处理方式都不同，所以拆成两个接口很合理。

## 4. API 层为什么不直接调用所有节点

如果 API 层直接知道：

1. intent 怎么判
2. rewrite 怎么写
3. search 怎么并发
4. critic 怎么回退

那 API 就会迅速膨胀成“上帝类”。

所以正确做法是：

- API 只负责接入协议
- Service 负责编排
- Graph 负责智能流程

## 5. Service 层的价值是什么

`app/services/investor_service.py` 常被初学者低估，但它很重要。

它通常负责：

1. 调用 Agent 工作流
2. 封装业务输入输出
3. 处理结果收敛
4. 做异步落库、审计等边缘动作

这让 API 不会太重，也让 Graph 不必关心过多外层业务细节。

## 6. `run_investor_flow()` 这种函数为什么合理

因为它相当于“Python 业务入口”。

它的职责不是亲自推理，而是：

1. 接住 API 层传来的参数
2. 调用 `multi_graph_agent`
3. 收集流式事件或最终答案
4. 处理后续业务动作，比如异步保存聊天记录

这和 Java 里典型的 Service 方法非常接近。

## 7. 为什么最终答案常常异步落库

因为用户体验优先。

如果你每一步都等数据库写完再回给前端，流式首包和整体响应都会变慢。

所以更工程化的思路是：

1. 先把结果给用户
2. 再异步做审计持久化

这是一种很典型的“主链路优先、附属链路异步化”的设计。

## 8. 这一层最值得学的思想

1. API 只处理协议，不做复杂业务
2. Service 负责业务编排，不做底层推理细节
3. Graph 负责智能工作流，不关心 HTTP 细节

这就是清晰分层。

## 9. 面试里怎么讲这一层

可以这么说：

> 我把 Python 服务分成了 API、Service 和 Graph 三层。API 负责 HTTP 协议和流式响应封装，Service 作为业务编排入口，负责调用 Agent 并处理审计落库，真正的智能决策和回退逻辑放在 LangGraph 里。这样每层职责边界比较清晰，后续排查和扩展都更容易。

## 10. 这一篇你最该记住的结论

1. API 层不是业务层。
2. Service 层不是可有可无，它是编排边界。
3. Agent 项目如果分层清晰，后面改流式、改模型、改图结构都会轻松很多。

# 09 Token 预算与性能思维

## 1. `max_completion_tokens` 控制的到底是什么

它控制的是：

- 本次模型输出最多能生成多少 token

不是：

1. 模型一生只能用多少 token
2. 整个流程总共只能用多少 token
3. 账户总额度

所以它是“单次输出上限”，不是“全系统总预算开关”。

## 2. 为什么它通常放在节点级别控制

因为每个节点职责不同。

比如：

1. `intent` 只做分类，几十到几百 token 就够
2. `rewrite` 只做查询改写，不需要很长
3. `critic` 只做评审，也不需要太长
4. `answer` 才是最可能需要大量输出的节点

这就是为什么 Agent 项目里更合理的做法是“按节点预算”。

## 3. 能不能直接控制整个流程总 token

没有特别傻瓜式的一键开关。

原因很简单：

1. 流程节点数是动态的
2. 有条件路由
3. 有 critic 回退
4. 输入长度和检索长度也不固定

所以全流程 token 消耗天然是动态值。

## 4. 标准工程做法是什么

通常是两层控制：

1. 每个节点限制输出上限
2. 在 `AgentState` 里累计总 token，再做预算判断

比如：

- `total_tokens` 超过某阈值，就不再 retry
- 如果预算紧张，就让 answer 节点缩短输出

## 5. 为什么“裁输入”也很重要

token 成本不只是输出决定，输入也很关键。

输入通常来自：

1. system prompt
2. 用户问题
3. 历史消息
4. 检索知识片段
5. skill_context

所以要控成本，还要做：

1. prompt 精简
2. history 裁剪
3. knowledge 裁剪
4. top_k 控制

## 6. 性能优化要先抓哪几类点

### 6.1 阻塞 IO

比如同步 `requests.get()` 在 async 链路里会卡事件循环。

### 6.2 启动期重活

比如启动时就做很多向量表初始化和索引创建，会拉长冷启动。

### 6.3 多次无谓落库

如果一轮对话要做过多数据库写操作，吞吐会差。

### 6.4 过密日志

SSE 链路里如果每个小 chunk 都重日志，IO 成本会很高。

## 7. 为什么 Agent 项目的性能思维和普通 CRUD 不一样

普通 CRUD 常看：

1. SQL 慢不慢
2. 接口 QPS
3. 缓存命中率

Agent 项目还要额外看：

1. LLM 耗时
2. 检索耗时
3. 流式首 token 时间
4. 节点级 token 成本
5. critic 重试次数

## 8. 这一篇你最该记住的结论

1. `max_completion_tokens` 控的是单次输出，不是整条流程总额。
2. 全流程 token 控制通常靠“节点约束 + 状态累计”。
3. Agent 性能优化要同时看 LLM、检索、流式、IO 和回退闭环。

# 06 流式输出、SSE 与正文流

## 1. 先区分两种“流式”

很多人说流式输出时，脑子里只有“模型边写边吐字”。

但这个项目里其实有两类流式：

1. 阶段流式
2. 正文流式

### 阶段流式

比如：

- `accepted`
- `intent`
- `rewrite`
- `search`
- `answer`
- `critic`
- `done`

它让前端看到系统现在跑到哪一步了。

### 正文流式

比如：

- `content_delta`
- `final_answer`

它让前端正文边生成边显示。

## 2. 为什么阶段流式很重要

如果只有最终答案，用户等待时会很焦虑。

加入阶段流式后，用户至少知道：

1. 请求已接收
2. 正在判断意图
3. 正在检索
4. 正在生成答案

这不只是用户体验优化，也是调试利器。

## 3. 为什么正文流更难

因为正文流不是简单打印字符串，而是要处理：

1. LLM 的流式 token/chunk
2. LangGraph 消息事件
3. Python SSE 封装
4. Java 网关转发
5. 前端增量拼接

任何一层吃掉事件，页面上就会表现成“看起来不是流式”。

## 4. SSE 为什么适合这个场景

SSE 的优势：

1. 服务端单向推送简单
2. 浏览器原生支持
3. 适合连续事件而不是双向强交互
4. 对“思考过程 + 最终正文”这种场景非常友好

## 5. `step`、`content_delta`、`final_answer` 的职责分工

### `step`

告诉前端“系统现在在干什么”。

### `content_delta`

告诉前端“把这段正文继续拼上去”。

### `final_answer`

作为完整答案兜底，避免某些中间分片在链路里丢失后页面只显示半截。

## 6. 为什么要有 `final_answer` 兜底

因为真实系统里，流式链路可能受很多因素影响：

1. 子进程重载
2. 网关代理
3. 编码问题
4. chunk 丢失
5. 前端事件处理不一致

所以工程上常见做法是：

- 正常情况靠 `content_delta` 增量显示
- 最后再来一个 `final_answer` 做一致性兜底

## 7. 前端是怎么消费流式的

前端通常会：

1. 建立 EventSource 或 fetch stream
2. 收到 `step` 就追加思考过程
3. 收到 `content_delta` 就拼正文
4. 收到 `final_answer` 就做最终覆盖/兜底
5. 收到 `done` 就关闭流

这就形成了“阶段可见 + 正文持续生长”的体验。

## 8. 为什么之前会出现编码问题

Windows 下一个很常见的坑是：

1. 某些日志输出按 `GBK` 编码
2. 流式步骤或日志里带 emoji
3. 控制台输出失败
4. 异常打断 SSE 链路

这类问题的本质不是前端坏了，而是流式链路里混入了不兼容的控制台输出。

## 9. 这一篇你最该记住的结论

1. 流式不只有“正文 token 流”，还有“阶段流”。
2. 真正的流式体验依赖 Python、Java、前端三层都不吞事件。
3. `final_answer` 兜底不是多余，而是工程上的保险。

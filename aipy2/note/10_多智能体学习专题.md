# 10 多智能体学习专题

## 1. 先回答一个最常见的问题

当前这个项目是不是多智能体？

更准确的答案是：

> 现在它更像“单 Agent + 多节点工作流”，而不是严格意义上的多智能体系统。

## 2. 为什么它还不算严格多智能体

因为当前主要特征是：

1. 一张统一的 `StateGraph`
2. 一套共享 `AgentState`
3. 节点分工明确，但还不是独立 Agent 之间协作

也就是说：

- 它有“多步骤”
- 但还没有“多个独立角色大脑”

## 3. 那什么才更像多智能体

真正更典型的多智能体，往往会出现：

1. `Researcher Agent`
2. `Analyst Agent`
3. `Reviewer Agent`
4. `Coordinator Agent`

每个 Agent 有更清晰的角色边界、上下文边界、协作协议。

## 4. 当前项目离多智能体有多远

其实并不远，因为它已经具备一些很好的基础：

1. 节点职责比较清晰
2. 有 critic 这种“第二视角”
3. 有 skill/tool 这种能力拆分
4. 有共享状态和流程控制

这说明它已经具有多智能体演进土壤。

## 5. 为什么很多成熟项目先做单 Agent 工作流

原因不是“不会做多智能体”，而是工程理性：

1. 单 Agent 更好调试
2. 成本更低
3. 失败面更小
4. 数据链路更容易看清楚

多智能体虽然看起来更酷，但复杂度会显著上升。

## 6. 从当前项目怎么演进到多智能体

一个很自然的演进方式是：

### 方案一：逻辑角色化

先不真的拆多个独立进程，只在图内强化角色概念：

1. 检索者
2. 分析者
3. 评审者

### 方案二：技能角色化

把某些复杂 skill 做成更独立的 agent-like 单元。

### 方案三：真正多 Agent 协作

让不同 Agent 通过明确消息协议协作：

1. Researcher 只负责找证据
2. Analyst 只负责形成结论
3. Reviewer 只负责打回和挑错
4. Orchestrator 负责分配任务

## 7. 多智能体的代价也要看到

1. 状态同步更复杂
2. token 成本更高
3. 调试更麻烦
4. 观测链路更长
5. 失败点更多

所以：

> 多智能体不是默认更高级，而是适用于更复杂协作问题。

## 8. 面试里怎么回答“你们是不是多智能体”

推荐这样回答：

> 当前项目核心是单 Agent 的状态化工作流，但已经具备多智能体演进基础。我们通过 intent、rewrite、search、answer、critic 这些节点实现了职责分离和自我评审闭环。如果业务继续复杂化，可以进一步把 research、analysis、review 拆成独立 agent 协作。

## 9. 这一篇你最该记住的结论

1. 多节点工作流不等于多智能体。
2. 当前项目最准确定位是“单 Agent 工作流”。
3. 真正的多智能体价值在于角色独立协作，而不是节点数量变多。

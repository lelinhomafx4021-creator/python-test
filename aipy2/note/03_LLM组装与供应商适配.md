# 03 LLM 组装与供应商适配

## 1. 为什么项目里要有 `get_llm()`

很多初学者会问：

“既然就是创建一个 `ChatOpenAI(...)`，为什么还要包一层函数？”

答案是：因为这不是单纯创建对象，而是在做“统一组装”。

`get_llm()` 的职责通常包括：

1. 统一模型名
2. 统一 API key 获取方式
3. 统一 base_url
4. 统一温度等基础参数
5. 兼容流式参数
6. 兼容不同供应商的参数差异

## 2. 这层在架构里的位置

你可以把它想成三层：

1. 业务层：`graph`、`service` 只知道“我要一个能工作的模型对象”
2. 适配层：`llm.py` 负责把业务要求翻译成 SDK 需要的参数
3. 供应商层：DeepSeek、小米、OpenAI 等模型提供商

所以 `llm.py` 本质上是“适配器层”。

## 3. 为什么 DeepSeek 版代码比最简版长

最简版可能只需要：

```python
def get_llm(temperature: float = 0.2):
    return ChatOpenAI(...)
```

但工程项目里常常还要兼容：

1. `streaming=True`
2. `max_completion_tokens=...`
3. 供应商参数名差异

所以就会比最简版多一些代码。

这不是无意义复杂，而是为了不让上层到处感知供应商差异。

## 4. 为什么要把 `max_completion_tokens` 映射成 `max_tokens`

这里体现的就是“OpenAI 兼容 API 不完全一致”的现实。

项目内部想统一用更语义化的名字：

- `max_completion_tokens`

但供应商底层 API 真正吃的参数可能是：

- `max_tokens`

于是我们就在 `get_llm()` 里做一层翻译。

这就是典型的接口适配思想。

## 5. 和小米版对比能学到什么

### 小米版关注点

- 模型名不同
- key 名不同
- base_url 不同
- 有的参数可以直接传

### DeepSeek 版关注点

- 模型名不同
- key 名不同
- base_url 不同
- 某些参数需要适配

结论是：

> 不是“模型对象必须写很多代码”，而是“服务商差异 + 工程统一入口”让这层看起来稍微长一些。

## 6. `streaming` 为什么要放在这里

因为上层节点会直接依赖流式能力。

比如：

- 非流式节点只关心最终文本
- 流式回答节点需要边生成边往外吐

如果 `get_llm()` 不支持 `streaming`，调用方就要自己去 new 一套流式模型，那统一性就没了。

## 7. 学习这层最重要的不是 SDK，而是思想

要学的不是“某个函数怎么写”，而是：

1. 为什么模型接入不能散落在全项目
2. 为什么要统一入口
3. 为什么供应商差异要在底层适配
4. 为什么上层业务不应该知道具体 provider 的细节

## 8. 一个很有面试价值的说法

> 我把 LLM 接入做成了单独的适配层。业务层只依赖 `get_llm()`，而模型名、key、base_url、流式开关、token 参数兼容都被收敛在这一层。这样后续切换供应商时，只需要改一处，而不需要改整个 Agent 工作流。

## 9. 这一篇你最该记住的结论

1. `llm.py` 不是“多余封装”，而是适配层。
2. DeepSeek 和小米的差异主要体现在模型名、key、base_url、参数兼容。
3. 工程里最值钱的是“把变化点集中”，不是“把代码写到最短”。

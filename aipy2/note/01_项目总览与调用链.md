# 01 项目总览与调用链

## 1. 这个 Python 项目到底在做什么

这是一个投研问答 Agent 服务。它的任务不是单纯聊天，而是把“用户问题 -> 理解 -> 检索 -> 回答 -> 评审 -> 回退”串成一条完整链路。

一句话概括：

> 这是一个基于 `FastAPI + LangGraph + RAG + PostgreSQL(pgvector)` 的流式投研 Agent 系统。

## 2. 为什么它不是“直接调用 LLM”

很多初学者会以为：

1. 用户发问题
2. 后端调模型
3. 模型吐答案

但这个项目不是这样。它多了很多工程层：

1. 先判断问题类型
2. 决定要不要走知识库
3. 需要的话先改写 query
4. 并发检索向量/BM25/Web/行情
5. 汇总知识后再回答
6. 再让 critic 检查答案是否可靠
7. 不可靠就回退重做

这就是 Agent 和普通聊天接口最大的区别：

- 普通聊天偏“直接生成”
- Agent 偏“带流程的决策与执行”

## 3. 从分层看整个系统

### 3.1 入口层

- `main.py`
- `app/api/v1/chat.py`

负责接 HTTP 请求、注册路由、中间件、生命周期。

### 3.2 编排层

- `app/services/investor_service.py`

负责把 API 请求交给 Agent，并处理最终落库这类业务动作。

### 3.3 Agent 大脑层

- `app/graph/investor_graph.py`

这里定义 LangGraph 的状态、节点、边、路由、流式事件。

### 3.4 能力层

- `app/skills/stock_analysis_skill.py`
- `app/tools/retriever_tool.py`
- `app/tools/stockdata_tool.py`

这里是真正做检索、行情、结构化分析的地方。

### 3.5 RAG 与存储层

- `app/rag/vector_store.py`
- `app/core/db.py`
- `app/models/chat_turn.py`

负责向量检索、表结构、审计和持久化。

## 4. 一次请求的完整调用链

建议你把下面这条链背下来：

1. 前端发起 `/gateway/ai/chat/stream`
2. Java 网关转发到 Python `/ai/v1/chat/stream`
3. FastAPI 路由接住请求
4. 路由调用 `investor_service.run_investor_flow(...)`
5. Service 调用 `multi_graph_agent.ask_stream_events(...)`
6. LangGraph 开始跑节点
7. 节点输出 `step`、`content_delta`、`final_answer`
8. FastAPI 把这些事件包装成 SSE
9. Java 网关把 SSE 原样代理回前端
10. 前端边收边显示
11. 最终答案异步落库

## 5. 为什么“画调用链”这么重要

因为这个项目不是单文件脚本，而是典型的分层系统。如果你不知道一次请求怎么走，你就会觉得“每个文件都很复杂”。

一旦你把调用链搞清楚，就会发现：

- API 层负责接
- Service 层负责转
- Graph 层负责想
- Tool/Skill 层负责做
- DB 层负责记

## 6. 用 Java 思维类比

如果你是 Java 背景，可以这样类比：

- `FastAPI` 类似 `Spring Boot Controller`
- `Pydantic` 类似 `DTO + Bean Validation`
- `Service` 层和 Java 很像
- `LangGraph` 类似“带状态的工作流引擎”
- `AgentState` 类似“贯穿链路的上下文对象”
- `SSE` 类似“服务端持续推送响应”

## 7. 这一篇你最该记住的结论

1. 项目主线不是“问模型”，而是“跑工作流”。
2. 最值得先掌握的是请求调用链。
3. 只要你能画出这条链，后面看代码就会轻松很多。

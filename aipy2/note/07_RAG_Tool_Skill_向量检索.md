# 07 RAG、Tool、Skill 与向量检索

## 1. 为什么 Agent 项目离不开 RAG

如果只靠大模型参数记忆，问题会很多：

1. 信息可能过时
2. 事实依据不明确
3. 无法接入你自己的私有知识库
4. 很难做投研这类强调证据的场景

所以 RAG 的意义是：

> 先找资料，再回答。

## 2. Tool 和 Skill 的区别

### Tool

更像原子能力：

1. 检索器
2. 行情查询
3. web 搜索
4. 向量查询

### Skill

更像高阶能力编排：

1. 调多个 tool
2. 做结果组装
3. 做结构化分析
4. 给 graph 提供更完整能力

简单讲：

- Tool 偏单一动作
- Skill 偏组合能力

## 3. 为什么这个项目不只做向量检索

纯向量检索有局限：

1. 对精确关键词不一定稳
2. 对短 query 有时不如关键词检索
3. 对时效性内容天然不足

所以项目里通常会组合：

1. 向量检索
2. BM25
3. Web 搜索

这是典型的混合检索思路。

## 4. `rewrite_node` 为什么是 RAG 质量关键

很多人只盯着 vector store，但其实 query 改写经常更关键。

原问题如果太口语化，检索器会很痛苦。改写后：

1. 关键词更明确
2. 检索召回更稳定
3. 融合排序效果更好

所以：

> RAG 不只是“库和向量”，还包括 query engineering。

## 5. `retriever_tool.py` 在干什么

它不是只查一个地方，而是负责：

1. 拉向量结果
2. 拉 BM25 结果
3. 拉 Web 结果
4. 把结果做融合
5. 再进行重排或裁剪

这就是“多路召回 + 融合”的检索结构。

## 6. BM25 为什么仍然有价值

BM25 是经典关键词检索算法，虽然听起来没“向量”那么时髦，但它非常实用。

它适合：

1. 精确词命中
2. 财报、股票名、行业名等关键词
3. 对 embedding 不稳时的兜底

所以现代 RAG 项目里，BM25 不是过时，而是重要补充。

## 7. RRF 融合为什么值得学

RRF 可以理解成：

- 不看每路原始分数是否同尺度
- 先按排名再融合

这样做的好处是：

1. 简单
2. 稳
3. 适合多路检索结果合并

它常常比你硬拼不同分数更靠谱。

## 8. `vector_store.py` 在做什么

这层负责：

1. 文档切块后的入库
2. embedding 生成
3. 向量字段存储
4. 相似度搜索
5. 向量索引维护

在这个项目里，它对应的是 `PostgreSQL + pgvector` 方案。

## 9. `stock_analysis_skill.py` 值得学什么

它体现了一个很好的思想：

1. Graph 不直接碰过多细节
2. Skill 作为中间组合层，把检索和行情工具包装成更像“业务能力”的东西

这能让 Agent 图保持干净，不至于每个节点都写一堆底层逻辑。

## 10. 这一篇你最该记住的结论

1. RAG 的本质是“先取证，再生成”。
2. Tool 是原子能力，Skill 是组合能力。
3. 高质量 RAG 依赖查询改写、多路召回、结果融合，而不只是一个向量库。
